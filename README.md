# ResolveHub — Smart Complaint Management System

A full-stack complaint management platform built with **Next.js**, **TypeScript**,
**Tailwind CSS** and **Supabase**. Users submit and track complaints, staff action
the ones assigned to them, and administrators triage, assign, resolve and analyse
everything from a single dashboard.

Every figure and every list in the running application is read live from
PostgreSQL. There is no mock data, no hardcoded statistics and no fake
authentication anywhere in the codebase.

## 1. Problem statement

Institutions, campuses and offices usually collect complaints through paper
forms, email threads or informal conversations. That approach loses track of
issues, gives the complainant no visibility after submission, makes it
impossible to hold anyone accountable, and produces no data that management can
act on.

ResolveHub replaces that with a single transparent platform where an issue is
recorded once, routed to a responsible person, tracked through a published
workflow, and measured after resolution.

## 2. Objectives

- Give complainants a single place to submit an issue with evidence, and let
  them follow its progress without having to ask anyone.
- Give administrators full visibility and control: triage, assign, prioritise,
  resolve, reject, and see the numbers.
- Give staff a focused queue of only the work assigned to them.
- Enforce all of the above at the **database** layer with Row Level Security, so
  the rules hold even if the UI is bypassed.
- Produce honest analytics (resolution rate, average resolution time, feedback
  ratings) computed from real timestamps.

## 4. User roles

| Role | How it is granted | Scope |
| --- | --- | --- |
| `user` | **Automatic** on registration. The database trigger hard-codes this value; the registration form has no role field at all. | Own complaints, own notifications, feedback on own resolved complaints |
| `staff` | Created by an administrator from **Admin → Staff** using the server-only service-role key | Complaints assigned to them |
| `admin` | Promoted in the database (see [Assigning roles safely](#assigning-roles-safely)) | Everything |

A user can never escalate their own role: the `guard_profile_update` trigger
rejects any role or activation change made by a non-admin, and the
`profiles: update own` RLS policy only permits a user to write their own profile.

```
                    │      User Browser       │
                    │  Next.js / React / RSC  │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │      Next.js Server     │
                    │  Server Components      │
                    │  Server Actions         │
                    │  middleware.ts          │
                    └────────────┬────────────┘
                                 │  @supabase/ssr
                    ┌────────────▼────────────┐
                    │     Supabase Client     │
                    └────────────┬────────────┘
                                 │
        ┌────────────────────────┼────────────────────────┐
        │                        │                        │
┌───────▼────────┐    ┌──────────▼─────────┐    ┌─────────▼────────┐
│ Supabase Auth  │    │ PostgreSQL         │    │ Supabase Storage │
│ (JWT, cookies) │    │ + Row Level        │    │ complaint-images │
│                │    │   Security         │    │ avatars          │
└────────────────┘    └──────────┬─────────┘    └──────────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │   Supabase Realtime     │
                    │  (RLS-aware broadcast)  │
                    └─────────────────────────┘
```

**Request flow.** `middleware.ts` refreshes the session cookie and enforces
authentication and the `/admin` role gate. Pages then re-check the user with
`getUser()` and query through the user-scoped server client, so **every query
runs under that user's RLS policies**. Mutations go through Server Actions which
verify the caller's role again before writing.

**Why two Supabase clients.**

| Client | Key | Used for |
| --- | --- | --- |
| `lib/supabase/client.ts` | anon (browser) | Auth state, image uploads, Realtime subscriptions |
| `lib/supabase/server.ts` | anon + session cookies | All reads and normal writes |
| `lib/supabase/admin.ts` | **service role** | Only creating / deleting Auth users for staff accounts |

`lib/supabase/admin.ts` imports `server-only`, so pulling it into a client
bundle is a **build error** — the service-role key physically cannot reach the
browser.

## 7. Database architecture

Six application tables plus two storage buckets:

```
profiles ──────┐
    │          │
    │          │ (assigned_to)
    │          ▼
    │      complaints ──────┐
    │          │           │
    │          ▼           ▼
    │  complaint_status_  feedback
    │      history
    │
    └────────► notifications

categories ─────► complaints
```

Key mechanisms:

- **`on_auth_user_created` trigger** — creates a `profiles` row for every new
  `auth.users` row, always with `role = 'user'`.
- **`generate_complaint_number()` trigger** — assigns `CMP-000001` from
  `complaint_number_seq` on insert.
- **`log_complaint_status_change()` trigger** — on insert and on every status
  change, writes a `complaint_status_history` row, creates a notification for
  the complainant, stamps `resolved_at` when the status becomes `Resolved`, and
  refreshes `updated_at`.
- **`notify_assignee()` trigger** — notifies the staff member when a complaint
  is assigned to them.
- **`guard_complaint_update()` trigger** — the real enforcement of "users cannot
  change status", "staff cannot reassign", "users cannot edit after review".
- **`guard_profile_update()` trigger** — the real enforcement of "users cannot
  change their own role".
- **`guard_feedback_insert()` trigger** — feedback is only allowed on your own
  complaint, and only once it is Resolved or Closed.
- **`admin_analytics()` function** — a `SECURITY DEFINER` function that refuses
  to run for non-admins and returns every dashboard figure as JSON.

## 9. ER diagram description

- **auth.users 1 ── 1 profiles** — one profile per authenticated account. The
  profile is created automatically by a trigger.
- **profiles 1 ── * complaints** (`user_id`) — a complainant raises many
  complaints.
- **profiles 1 ── * complaints** (`assigned_to`) — a staff member can be
  assigned many complaints. Nullable, and `ON DELETE SET NULL` so deleting a
  staff account does not destroy complaint history.
- **categories 1 ── * complaints** (`category_id`) — a category groups many
  complaints. `ON DELETE RESTRICT` is what stops an in-use category being
  deleted.
- **complaints 1 ── * complaint_status_history** (`complaint_id`) — the full
  audit trail of one complaint.
- **profiles 1 ── * complaint_status_history** (`changed_by`) — who made each
  change.
- **complaints 1 ── 1 feedback** (`complaint_id`, unique) — at most one rating
  per complaint.
- **profiles 1 ── * feedback** (`user_id`) — the author of the rating.
- **profiles 1 ── * notifications** (`user_id`) — notifications belong to one
  account.
- **complaints 1 ── * notifications** (`complaint_id`) — a notification usually
  points at the complaint it is about.

## 10. Authentication flow

**Registration**

1. The user submits full name, email, password and confirmation.
2. The Zod schema validates the input; **there is no role field**.
3. `supabase.auth.signUp()` creates the Auth user with `full_name` in metadata.
4. The `on_auth_user_created` trigger inserts the `profiles` row with
   `role = 'user'` — hard-coded, never read from client metadata.
5. If the project requires email confirmation the user is told to confirm and
   sent to `/login`; otherwise they land on `/dashboard`.

**Login**

1. `supabase.auth.signInWithPassword()`.
2. Supabase `setAll` writes the session into HTTP-only cookies via
   `@supabase/ssr`.
3. The role is read and the user is sent to `/admin` or `/dashboard`.
4. Deactivated staff accounts are signed out immediately with an explanation.

**Every subsequent request**

1. `middleware.ts` calls `supabase.auth.getUser()` — which **revalidates the JWT
   with Supabase Auth**, unlike `getSession()`, so a tampered cookie cannot be
   trusted.
2. Protected paths redirect to `/login?next=…` when there is no session.
3. `/admin/*` redirects to `/dashboard` unless the database says the role is
   `admin`.
4. `/login` and `/register` redirect an already-signed-in user to their
   dashboard.
5. Pages and Server Actions re-check independently — the middleware is the first
   gate, not the only one.

**Sign out** calls `supabase.auth.signOut()`, which clears the cookies, then
redirects to `/login`.

**Email confirmation / recovery** links land on `/auth/callback`, which
exchanges the one-time code (or `token_hash`) for a session.

## 11. Complaint workflow

```
User submits complaint
        ↓
Complaint number generated (CMP-000001)
        ↓
Status = Submitted ──────────────► Admin reviews
                                        ↓
                                  Status = Under Review
                                        ↓
                                  Admin assigns staff
                                        ↓
                                  Status = Assigned
                                        ↓
                                  Staff starts work
                                        ↓
                                  Status = In Progress
                                        ↓
                                  Staff resolves the issue
                                        ↓
                                  Status = Resolved  (resolved_at stamped)
                                        ↓
                                  User reviews & submits feedback
                                        ↓
                                  Complaint = Closed
```

`Rejected` is reachable from any non-final state, and **requires a remark**.

**Valid transitions** (enforced in `lib/constants.ts` for the friendly message,
and independently by the database trigger):

| From | Allowed next |
| --- | --- |
| `Submitted` | `Under Review`, `Assigned`, `Rejected` |
| `Under Review` | `Assigned`, `In Progress`, `Rejected` |
| `Assigned` | `In Progress`, `Resolved`, `Rejected`, `Under Review` |
| `In Progress` | `Resolved`, `Rejected`, `Assigned` |
| `Resolved` | `Closed`, `In Progress` |
| `Closed` | *(final)* |
| `Rejected` | `Under Review` |

A transition such as `Submitted → Closed` is refused with a readable message and
would be refused by the database even if the UI were bypassed.

## 14. Supabase setup

1. Create a project at <https://supabase.com/dashboard>.
2. Open **Project Settings → API** and copy:
   - **Project URL** → `NEXT_PUBLIC_SUPABASE_URL`
   - **anon / publishable key** → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - **service_role key** → `SUPABASE_SERVICE_ROLE_KEY` *(optional, server-only)*
3. Paste them into `.env.local` and restart the dev server.
4. Run the migration (next section).
5. Under **Authentication → Providers**, email is enabled by default.
   - To test without clicking confirmation links, turn **Confirm email** off in
     **Authentication → Sign In / Providers → Email**.
   - With it on, new users must confirm before signing in (also handled).
6. Optionally run `supabase/seed.sql` for demo data.

### Assigning roles safely

There is deliberately **no way to select `admin` during registration**.

To promote an account, first register it normally through `/register`, then run
one of these in the Supabase SQL Editor — it is a privileged operation, which is
exactly why it is not exposed to the client:

```sql
-- Promote to staff
update public.profiles
set role = 'staff'
where email = 'staff@college.edu';

-- Promote to admin
update public.profiles
set role = 'admin'
where email = 'admin@college.edu';
```

Alternatively, use **Admin → Staff** in the running application, which creates a
staff account server-side with the service role.

> The SQL editor runs with privileges that bypass RLS. These statements do not
> work from the client, which is the point.

## 15. Database migration instructions

The whole schema is one idempotent file:

```
supabase/migrations/20260914000000_init_resolvehub.sql
```

It creates the tables, constraints, indexes, triggers, functions, RLS policies,
storage policies, the realtime publication and the `admin_analytics()` function.

### Option A — Supabase SQL Editor (no tooling required)

1. Open your project → **SQL Editor** → **New query**.
2. Paste the entire contents of the migration file and click **Run**.
3. Optionally paste `supabase/seed.sql` and run that too.

### Option B — Supabase CLI (recommended)

```bash
npm install -g supabase          # or: brew install supabase/tap/supabase
supabase login
supabase link --project-ref <your-project-ref>
supabase db push                 # applies supabase/migrations/*
```

### Option C — Local Supabase stack (requires Docker)

```bash
supabase start                   # starts Postgres, Auth, Storage, Realtime
supabase db reset                # applies migrations + seed.sql
```

The local stack serves the API at `http://127.0.0.1:54321` with the anon key
printed by `supabase start`. Put those in `.env.local`.

### Re-running safely

Every statement uses `create table if not exists`, `drop policy if exists`
before `create policy`, and `on conflict do nothing` for seeds, so re-running
the migration does not fail or duplicate data.

## 16. Storage bucket setup

The migration creates both buckets and their policies. To verify or create them
manually, go to **Storage → Buckets**:

| Bucket | Public | Size limit | Allowed types |
| --- | --- | --- | --- |
| `complaint-images` | yes | 5 MB | `image/jpeg`, `image/jpg`, `image/png`, `image/webp` |
| `avatars` | yes | 2 MB | `image/jpeg`, `image/jpg`, `image/png`, `image/webp` |

**Object layout.** Files are stored as `<user_id>/<uuid>.<ext>`. The first path
segment is the owner's user id, and the storage policies check exactly that:

```sql
create policy "complaint-images: owner upload"
  on storage.objects for insert to authenticated
  with check (
    bucket_id = 'complaint-images'
    and (storage.foldername(name))[1] = auth.uid()::text
  );
```

So a user can only ever write inside their own folder — even with a crafted
request. Buckets are public-read so complaint images can be displayed without
signing every URL, which is standard for non-sensitive evidence photos.

**Upload path.** The browser uploads directly to Storage using the user's own
session (no service-role key involved). Only the resulting object *path* is sent
with the form; the server rebuilds the public URL from it rather than trusting a
client-supplied URL.

## 17. Row Level Security explained

RLS is enabled on all six application tables and revoked for the `anon` role
entirely. Nothing is readable without an authenticated session.

Role checks inside policies go through `SECURITY DEFINER` helper functions
(`is_admin()`, `is_staff()`, `is_admin_or_staff()`). These read `profiles` as
their owner, which bypasses RLS — this is what prevents infinite recursion when
a policy on `profiles` needs to know the caller's own role.

### What each role can do

**`user` (authenticated)**

| Table | Read | Write |
| --- | --- | --- |
| `profiles` | own row only | own row only (name, avatar — role and activation are blocked by a trigger) |
| `categories` | all | none |
| `complaints` | own only | insert own; update own only while `status = 'Submitted'`; delete own only while `Submitted` |
| `complaint_status_history` | own complaints only | none |
| `feedback` | own only | insert own, only when the complaint is `Resolved` / `Closed` |
| `notifications` | own only | update own (`is_read`), delete own |

**`staff`**

Reads complaints where `assigned_to = auth.uid()`, their status history and
feedback, and can update status and notes for those complaints. Cannot reassign
(blocked by `guard_complaint_update`), cannot change roles, cannot read other
users' complaints.

**`admin`**

Full read and write across all six tables, including assignment, category
management and role changes.

### Defence in depth

Three independent layers must all agree:

1. **RLS policies** decide which rows exist for the caller at all.
2. **Triggers** (`guard_complaint_update`, `guard_profile_update`,
   `guard_feedback_insert`) reject illegal *changes* to rows that are visible —
   things RLS alone cannot express, like "you may edit this row but not this
   column".
3. **Server-side role checks** (`requireAdmin()`, `requireStaffOrAdmin()`) in
   every Server Action produce a friendly message before either of the above is
   reached.

The UI never decides anything on its own; hiding a button is presentation, not
security.
